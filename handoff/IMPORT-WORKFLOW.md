# 导入与回收工作流

核查日期：2026-10-24。此包已在本地准备并上传私有 GitHub 仓库；Figma 云端导入与运行尚未执行。请先读取 GITHUB-WORKFLOW.md 的最新连接状态与新旧 GitHub 集成区别。

当前按用户最新选择采用路线 A，GitHub 保留备份。新账号浏览器未显示新版 Clone from GitHub，GitHub 连接器安装流程也未完成。Codex 的 Figma 插件仍连接旧账号，服务端拒绝编辑新账号 Make 文件；需将插件重新连接到目标账号后使用官方代码导入工具。当前文件为空白工程，不能声称已导入作品集。不要把 ZIP 作为普通聊天附件上传后就视为可运行工程。

## 路线 A：先做一轮视觉实验

1. 解压 ZIP，选择包含 `package.json`、`index.html`、`src`、`public` 的工程根目录。不要只上传 `src`，也不要将 ZIP 当成普通聊天附件来期待自动运行。
2. 在 Figma Make 的代码工程导入/本地文件夹入口导入该根目录。若当前账户没有对应入口，可以让 Codex 通过官方 `send_code_to_figma` 导入新的独立 Make 文件；该流程会按服务端要求重新创建上传归档。无需先发布网站。
3. 等待安装并启动预览。首先核对主页、EN/中文、桌面滚动循环、`/demos/sleeve/index.html#/templates`；确认运行的是现有工程，再发设计修改提示词。不要让模型只凭提示从空白重新生成。
4. 在账户可用的模型选择器中选择希望使用的 Claude，将 `CLAUDE-PROMPT.txt` 全文发出。入口文字、模型选项和权限以当前界面为准。
5. 第一轮完成后检查首页、商业封面、交互 UI 封面与衔接；同一 Make 会话可以继续处理完整清单中的其余项。
6. 下载修改后的源码 ZIP，交给本地 Codex 放进新的候选版本目录；比较更改、恢复完整视频、重新构建和浏览器验证。确认后再决定是否作为正式下一版。

## 路线 B：长期往返修改（GitHub）

1. 从本工程建立独立仓库，保留初始版本，使用实验分支。默认建议私有仓库；需用户明确选择并连接 GitHub 后再上传。
2. 在 Figma Make 通过 Clone from GitHub 选择仓库与分支。账户/团队需要具备对应连接和仓库访问权限。
3. Figma 修改在分支中提交，通过 PR 或提交差异回到本地；本地检查后再合并。
4. 依赖、完整大视频、原始 Adobe/UE 文件仍不必进入仓库。原始素材库保留在本地。

GitHub 的主要收益是版本追踪、差异审查和往返同步，不会自动提高视觉品质，也不会让 Figma 看见本机未上传的目录。文件夹导入的代码没有持续 GitHub 连接；之后下载源码回来属于手动回收。

## 能否一次要求全部改完？

可以。完整问题清单已经放进 `DESIGN-BRIEF.md`。本次默认提示词先实现首页与两张代表性封面，以便集中验证字体、色调、构图、真实交互和滚动编排。它们通过后再扩展到其他封面，减少全站做完再推翻的成本。

若要一次连续推进，可将主提示词最后的范围改为：

> 本轮执行 DESIGN-BRIEF.md 中全部首页与外层浏览问题。先完成首页、商业视觉、交互 UI 三个基准，再在同一轮继续推广到其余封面、About、摄影占位、归档、菜单、双语和循环衔接；每完成一段就验证，不必等我逐段确认。项目内部展示、作品事实和未提供的摄影素材仍不改。最终逐项报告完成、部分完成和未完成，不能把只换颜色或增加视差算作完整解决。

读取到工程解决的是上下文缺失；审美判断仍需看真实预览。不要因为文件已上传，就声称模型已经理解所有素材或已经准确看到了参考站的动态表现。
